How LLMs are served

Serving a large language model is different from serving traditional backend traffic. There are different bottlenecks, constraints, and resources required. We'll explore at a conceptual level the various strategies to effectively serve LLMs, and the tradeoffs between them.

1 · The problem

A GPU generating one token at a time is mostly waiting

To generate a single token, every weight of the model must be read from memory*. The weights are divided into layers, and a little math is done with each layer. Layers must be computed in order for a given token because the outputs of the computations of one layer become the inputs of the next. Each layer's weights are copied from VRAM onto the chip in small pieces before the math on them can happen, and that copy is limited by the GPU's memory bandwidth. With one token to compute, copying the weights takes far longer than doing the math on them, so the compute units spend most of their time waiting. Batching fixes this: many tokens share each copy of the weights, so the GPU gets more math done per byte it reads.

Generating a response has two phases. Prefill processes the prompt's tokens together (a long prompt in a few large chunks), so every prompt token shares each copy of the weights and the GPU stays busy. Decode then generates the answer one token at a time, and that is where the waiting happens. This guide is mostly about decode.

* Mixture-of-experts models work differently: each token reads the attention weights and only the few experts it is routed to, not every weight. See Expert parallel.

Batching: the bus loop analogy

Picture the model as a bus route: a loop with one stop for every layer. To produce a word, the bus has to drive the whole loop, and every rider on board gets their next word at the end of the lap. A lap costs about the same whether the bus carries one rider or a full bus, because the expensive part is driving the route (moving the weights through the GPU), not carrying passengers. So the trick is to fill the bus. That is called batching, and it is the first thing any serving system does before touching parallelism. The bus loop below lets you try it.

2 · One GPU

How to get the most out of one GPU

Two techniques do most of the work. Continuous batching refills the batch at every step, and the paged KV cache hands out each request's working memory a small page at a time, so at most one partly filled block per request is reserved ahead of use.

In bus terms: continuous batching lets riders step off the moment their answer is done and puts someone new in that seat on the very next lap, so a seat is refilled on the next lap whenever the luggage rack has room for the next rider's bags. Paging is how the luggage rack works: each rider gets rack space one bag at a time as their luggage grows, instead of reserving room for the most luggage anyone could ever bring.

Continuous batching, step by step

Each step is one decode iteration for the whole batch: every request in a slot gets one more token. Lighter bar = prompt, solid = generated tokens, dashed outline ending at a tick = the rest of the answer. A real engine cannot know where the answer ends; the tick is drawn for illustration. "Queued" counts requests that have arrived but have no slot yet. Toy scale: 4 tokens per KV block.

Things to try. At the default 0.20 new requests per step, watch a slot empty the step its answer finishes and a queued request take it on the next step. Drag past 0.29 and more requests arrive than finish, so the queue grows without limit: that is the capacity of 8 slots when answers average about 27 tokens. Watch the KV grid too: each request's blocks grow one at a time as it generates and are freed the moment it finishes.

Iteration-level scheduling

Serving engines schedule at the granularity of a single model iteration: at every step, finished sequences leave and waiting ones join. If a batch instead had to wait for its longest request, finished requests would hold idle slots while new arrivals queued.

vLLM's scheduler output is just a map of request id to number of tokens to process this step. Prefill and decode are not distinguished, which is what lets chunked prefill, prefix caching and speculative decoding share one scheduler. Chunked prefill is on by default: decodes are scheduled first, then prompt chunks fill the remaining token budget, so a long prompt never stalls everyone else's next token.

The paged KV cache

Each token's keys and values must be kept for the rest of the request. Reserving one contiguous region per request, sized for the maximum possible length, would leave most of that memory unused, because most requests stop well short of the maximum. Instead, the engine allocates fixed-size blocks on demand, like virtual memory pages (vLLM calls this PagedAttention and uses 64 tokens per block by default), so the only waste is the unfilled part of each request's last block, and far more requests fit in the batch.

Paging has a cost. The engine admits a request when there is room for its prompt, but it cannot know how long the answer will be, and every running request adds one token to its cache each step. If the pool runs out mid-answer, the engine preempts a request. In vLLM, it frees all of the most recently admitted request's blocks and puts that request back at the front of the queue. When space opens up, it rebuilds the request's cache by running prefill over the prompt plus every token generated so far, then continues. The other requests are unaffected. The preempted user sees their answer pause, and the GPU redoes work it already did. Occasional preemptions are the price of not reserving memory; frequent ones mean the cache is too small for the load, and the fix is a lower cap on concurrent requests or more memory for the cache.

3 · Four ways to split

Tensor, Pipeline, Data and Expert

When batching alone is not enough, because the model does not fit on one GPU or one GPU cannot serve enough traffic, the model is split or copied across GPUs. Each strategy answers two questions: which GPU holds which weights, and which GPUs touch a given token.

TENSOR PARALLEL

Every GPU works on every token

Each weight matrix is cut into N slices. One batch runs on all N GPUs at the same time, and twice per layer, after attention and after the MLP, the partial results are summed. Lowest latency per token, highest demand on the interconnect.

In plain terms. Every GPU holds a slice of every layer. For each word, all of them work on their own slice at the same time, then combine their results before moving to the next layer. One word comes out faster and no GPU needs the whole model. But they combine results twice per layer, which is dozens of times per word, so it pays off most over a very fast link such as NVLink inside one server.

How it keeps GPUs busy

The attention heads and the MLP's hidden dimension are independent along one axis, so each GPU multiplies its slice without talking to anyone. Splitting the first matrix of each pair by columns and the second by rows means a transformer block needs only two all-reduces in the forward pass. Because every GPU streams only 1/N of the weights per step, the memory-bound decode step gets up to N× shorter (less in practice, because the all-reduces add a fixed cost), which is why TP lowers per-token latency, not only memory.

The price is the all-reduce. It sits on the critical path and cannot overlap with the compute it depends on. The messages are small, so their cost is mostly fixed latency rather than bandwidth. Efficiency drops sharply once TP grows past one server, so keep TP within the GPUs of one node and pipeline across nodes.

Strengths

  • Lowest time per token of any split
  • Frees memory on every GPU for KV cache, so bigger batches and longer contexts
  • Simple: one process group, one endpoint, one flag

Costs

  • Needs fast links; over PCIe or Ethernet the all-reduce can cost more than it saves
  • Diminishing returns: each doubling of TP saves less, because the per-layer all-reduce does not shrink as GPUs are added
  • All GPUs fail together; a single GPU fault stops the whole replica
  • Attention heads must divide evenly; past the KV-head count, KV cache is replicated, not sharded

Business use cases

Interactive assistant on a model too big for one GPUUsers watch every token stream in. Tensor parallelism across the GPUs of one server gives the shortest time per token, because every GPU works on every token.
Agent loops with tight time budgetsAn agent that makes many model calls per task multiplies latency. Tensor parallelism buys the fastest single-stream decode available on the hardware.
A model that fits in one server but not on one GPUThe standard next step after one GPU, as long as the GPUs are joined by NVLink-class links. Keep the tensor-parallel degree at or below the model's number of KV heads, so the KV cache is split across GPUs instead of copied.
PIPELINE PARALLEL

An assembly line of layers

GPU 0 holds the first block of layers, GPU 1 the next, and so on. A batch walks from stage to stage. Only a small activation tensor crosses between GPUs, so the link can be slow, but a stage with nothing to do stands idle.

The bus version. A relay. The loop is split between drivers: driver 1 covers layers 1–20, driver 2 covers 21–40, and each hands the riders to the next. The route can now be longer than any one driver could manage, and drivers only meet at handoff points, so they can sit in different servers on an ordinary network. But a driver waiting for the next handoff sits idle. That idle time is the pipeline bubble, and the fix is keeping several busloads in flight so every stretch stays busy. No rider gets their word faster than the full loop takes.

How it keeps GPUs busy (and when it does not)

A pipeline stage is busy only while a micro-batch is on it. With one batch in flight, N−1 of N stages wait. Engines hide the bubble by keeping as many micro-batches in flight as there are stages; vLLM's scheduler holds a queue of in-flight micro-batches equal to the pipeline size and finishes the oldest as soon as it returns. That needs enough concurrent requests to go around, which is why PP suits throughput-oriented workloads.

Even when full, PP does not make a single request faster: each token still visits every stage in sequence. What it buys is memory across slow links. Only activations cross between stages, once per stage per step, so two nodes joined by Ethernet or a workstation with PCIe-only cards can host a model neither could hold alone. The vLLM docs say it directly: on nodes without NVLink, use pipeline parallelism instead of tensor parallelism for higher throughput and lower communication overhead.

Strengths

  • Tolerates slow interconnects: PCIe, Ethernet, cross-node
  • Supports uneven GPU counts and uneven layer splits
  • Composes with TP: TP inside each node, PP across nodes

Costs

  • No per-token speed-up; latency is the sum of the stages
  • Bubbles when traffic is light: with fewer requests in flight than stages, some GPUs sit idle
  • Each stage needs enough micro-batches, so KV cache must hold more concurrent requests to reach the same utilisation as TP

Business use cases

A model bigger than one serverTensor parallelism inside each server, where the links are fast, and pipeline parallelism between servers, where only activations cross the slower network. The usual rule is tensor-parallel size = GPUs per server and pipeline-parallel size = number of servers. Per-token latency is higher than on one server.
Batch jobs when the model must be splitWith no user waiting, per-token latency does not matter. Keep enough requests in flight to fill every stage, and PCIe machines do the job without NVLink.
Workstations and PCIe-only cardsWithout NVLink, every tensor-parallel all-reduce crosses PCIe. Pipeline parallelism passes one small activation tensor between cards per stage instead, and it can split layers unevenly when the GPU count does not divide the model's attention heads. Tensor parallelism over PCIe still works across a few cards and gives lower latency at light load, so test both under real traffic.
DATA PARALLEL

More copies, more lanes

Every GPU (or every TP group) holds the entire model and serves its own stream of requests. For a dense model nothing is shared or synchronised, and capacity scales almost linearly with replicas. In a mixture-of-experts deployment, the data-parallel ranks step together, because their tokens meet at the shared experts.

The bus version. More buses on the same loop. Each bus has its own driver and its own riders, so nobody has to coordinate and capacity grows almost perfectly. If one bus breaks down, the others keep running. But a single rider's trip is no faster, and every bus is a full copy of the model, so each GPU (or tensor-parallel group) must hold all the weights. The bus loop in section 1 has a second bus to try.

How it keeps GPUs busy

Each replica runs its own continuous batch. Because replicas never wait on each other, utilisation depends only on whether the load balancer keeps each queue fed. Throughput scales almost linearly with the number of replicas. DP alone is not enough for the largest models, because each replica needs the full weights on its own GPUs.

The flip side is memory. Every replica pays the full weight cost, so with N GPUs and a model that just barely fits, DP leaves the least room for KV cache and therefore the smallest batch per GPU. When the model fits with plenty of room, throughput and cost favour replicas; when it barely fits, TP can win on both. Latency favours TP.

Strengths

  • Near-linear throughput scaling, no inter-GPU traffic
  • Fault isolation and simple autoscaling: add or remove replicas
  • Best cost per token for offline work when the model fits

Costs

  • Cannot speed up a single request
  • N copies of the weights; least KV cache per GPU
  • Prefix cache is per replica, so routing must be prefix-aware to reuse it

Business use cases

Customer support chatMany short conversations on a model that fits on one GPU. The limit is request volume, not model size: one copy per GPU behind a load balancer, each batching its own requests. Split a copy with tensor parallelism only if one GPU leaves too little KV cache for your conversation lengths.
Multi-tenant platforms with uptime targetsA failed copy costs only its share of capacity instead of an outage. Rolling upgrades drain one copy at a time.
Elastic trafficDaytime peaks and night-time troughs map directly onto the number of copies, which is what Kubernetes autoscalers and routers such as llm-d manage.
Offline batch processingSummaries, classification and evaluations have no user waiting, so cost per token is the only goal. Run one copy per GPU, or per the smallest group of GPUs the model fits on, allow as many requests in flight as the KV cache holds, and stop raising concurrency when throughput stops improving.
EXPERT PARALLEL

Spread the experts, replicate the attention

Mixture-of-experts models hold dozens to hundreds of expert MLPs per layer but use only a few per token. Expert parallelism gives each GPU a share of the experts and routes tokens to them, usually combined with data-parallel attention.

In plain terms. A mixture-of-experts model has many specialist sub-networks, called experts, in each layer, and each word uses only a few of them. Expert parallel puts different experts on different GPUs, sends each word to the GPUs holding its experts, and gathers the results back. Every GPU stays busy only when enough words flow through to reach all the experts, so this wants big batches and a fast network between GPUs.

How it keeps GPUs busy

Under TP, a MoE layer's experts are sliced thin across every GPU and each all-reduce still happens twice per layer. Under EP, whole experts live on one GPU, so the matrix multiplies stay large and efficient, and the collective becomes an all-to-all that moves only the tokens each expert needs. With only a few experts active per token, spreading the experts across many GPUs gathers more tokens for each expert, which keeps its matrix multiplies efficient, and each GPU reads fewer expert weights per step.

Attention is kept data-parallel because many large MoE models use attention with very few KV heads, or a single compressed latent per token (multi-head latent attention); TP would duplicate the latent projections and KV cache on every rank. Each DP rank owns its batch and KV cache, the experts are spread over TP×DP ranks, and the effective batch across the deployment becomes large enough to keep every expert working. This layout is called "wide EP".

Strengths

  • Fits very large MoE models on one server at low precision, and scales to racks
  • Keeps expert matrix multiplies large, so the GPU stays efficient
  • Cuts replicas needed for a target QPS, lowering cost per token

Costs

  • All-to-all over a slow network dominates the step; it works best when every GPU sits in one fast NVLink domain, such as a rack-scale system
  • Needs high, steady traffic to fill all experts; light load leaves experts idle
  • Hot experts imbalance GPUs; needs expert load balancing (EPLB)
  • Operationally complex: specialised all-to-all kernels, RDMA, lockstep DP ranks

Business use cases

A high-volume API on a very large MoE modelMany customers send heavy, steady traffic, so every step carries thousands of tokens. Spreading the experts across GPUs gives each expert enough of those tokens to keep its matrix multiplies large, and each expert is read from memory once per step for everyone's tokens. That is what brings the cost per token down. It needs a fast network for the all-to-all exchange.
A private assistant on one serverLarge-model answers on hardware you own. Expert parallelism spreads the experts over the server's GPUs so the whole model fits, and each token reads only the few experts it needs, so with a handful of users decode runs at about the speed of a much smaller model.

4 · Beyond parallelism

Other ways serving engines keep the GPU busy

Parallelism decides where the weights live. These features decide how little time is wasted around them.

Prefix caching
On by defaultKV blocks are hashed by their content and prefix; a repeated system prompt is not recomputed while its blocks stay cached. It costs almost nothing when nothing is shared, so it is safe to leave on.
Speculative decoding
Trade idle compute for tokensA draft (n-gram, EAGLE, MTP) proposes several tokens; the model verifies them in one step. Helps at low load, can hurt at high load where the GPU is already busy.
Async scheduling
On by defaultThe CPU prepares step N+1 while the GPU runs step N, closing the gaps between kernels.
CUDA graphs
FULL_AND_PIECEWISECaptures whole decode steps so dozens of small kernels launch as one, removing per-kernel launch overhead that dominates small batches.
Prefill/decode disaggregation
Separate GPU poolsCompute-bound prefill and memory-bound decode get their own GPUs and their own parallelism. Does not raise throughput; it makes tail latency predictable (p99 ITL 169 → 29 ms in one guide).
Context parallelism
Shard the sequencevLLM can also split very long prompts, or the KV cache during decode, across GPUs for long-context workloads.
5 · Glossary

Simple descriptions for technical terms

72 terms, grouped by topic. Words with a dotted underline elsewhere on the page link here, and hovering one shows its definition. Where the bus loop has a part for a term, the entry says which.

72 terms

The basics

Large language model (LLM)

A neural network trained on huge amounts of text to predict the next token. Chat assistants, coding tools and agents are all built on one.

See 1 · The problem

Model

The trained network: a fixed architecture plus the weights it learned.

On the bus: The whole loop route.

See The bus loop

Weights (parameters)

The numbers a model learned during training. A “70B” model has about 70 billion of them. Every token uses all of them, or the active share in a mixture-of-experts model, so where the weights live decides how a model is split across GPUs.

See 1 · The problem, 3 · Split visualizer

Layer

One of the identical blocks a model is stacked from. Every token passes through every layer, in order. Large models have from a few dozen to over a hundred.

On the bus: A stop on the loop.

See The bus loop, Pipeline parallel

Token

The unit a model reads and writes: a word, part of a word or a punctuation mark. In English a token averages about three quarters of a word. Models generate text one token at a time.

On the bus: One word, earned once per lap.

See 1 · The problem

Prompt

The text sent to the model: the user's message plus any instructions, documents or conversation history. Longer prompts take longer to process and use more KV cache.

On the bus: The rider's luggage.

See 2 · One GPU

Request

One call to the model: a prompt goes in and a generated answer comes out. A server handles many requests at once.

On the bus: One rider.

See 2 · One GPU, The bus loop

Inference

Running a trained model to produce output, as opposed to training it. Answering a chat message is inference.

See 1 · The problem

Serving

Running inference for many users at once behind an API, with goals for speed and cost. vLLM, SGLang and TensorRT-LLM are serving engines.

See 1 · The problem

GPU

Graphics processing unit: a chip with thousands of small cores and very fast memory, built for the matrix maths inside neural networks. Large models are split or copied across several GPUs.

See 3 · Split visualizer

vLLM

An open-source engine for serving language models. It calls its paged KV cache PagedAttention. This page uses it (version 0.34) for its examples and defaults.

See 2 · One GPU

Inside the model

Transformer

The architecture nearly every LLM uses. Each layer has an attention block, which mixes information between tokens, and an MLP block, which transforms each token on its own.

See Tensor parallel

Attention

The part of each layer that lets a token look back at earlier tokens to decide what matters. It needs the keys and values of every earlier token, which is why the KV cache exists.

See 2 · One GPU

Attention head

Attention is split into several independent heads that run side by side. Tensor parallelism hands each GPU a share of the heads, so the head count must divide evenly by the number of GPUs.

See Tensor parallel

Grouped-query attention (GQA) and KV heads

A design where several attention heads share one set of keys and values, which shrinks the KV cache. A model with 8 KV heads can split them across up to 8 GPUs with tensor parallelism; beyond that, KV heads have to be copied instead of split.

See Tensor parallel

Multi-head latent attention (MLA)

An attention design used by some large mixture-of-experts models. It compresses each token's keys and values into one small latent vector per layer, so the KV cache is several times smaller. With effectively one KV head, tensor parallelism would copy it to every GPU, so MLA models usually run attention data-parallel.

See Expert parallel

MLP (feed-forward block)

The second half of each layer: large matrix multiplies applied to each token separately. It holds most of a dense model's weights. In a mixture-of-experts model it is replaced by many experts.

See Tensor parallel, Expert parallel

Activations

The intermediate numbers a token produces as it moves through the layers. They are small compared with the weights, which is why pipeline parallelism can pass them between servers over a slow link.

See Pipeline parallel

Tensor

A multi-dimensional array of numbers. Weights, activations and the KV cache are all tensors. Tensor parallelism is named after splitting these arrays across GPUs.

See Tensor parallel

Mixture of experts (MoE)

A model whose MLP is replaced by many smaller experts, with a router choosing a few for each token. A large MoE model may store hundreds of billions of weights but use only a few tens of billions per token, so it computes like a much smaller model while needing the memory of a huge one.

See Expert parallel

Expert

One of the specialist MLPs inside a mixture-of-experts layer. Large models have dozens to hundreds per layer and send each token to a handful of them.

See Expert parallel

Memory and the KV cache

KV cache

The working memory each in-flight request needs. It grows with every token, and it shares the GPU's memory with the weights, so it usually limits how many requests fit at once.

On the bus: The luggage rack.

See 2 · One GPU, The bus loop

Paged KV cache (PagedAttention) and KV blocks

Storing the KV cache in small fixed-size blocks handed out as a request grows. Like virtual memory pages, it avoids reserving space a request may never use. vLLM calls this PagedAttention and uses 64 tokens per block by default.

On the bus: Rack space handed out one bag at a time.

See 2 · One GPU

Context window (context length)

The most tokens one request may hold, prompt plus answer. Longer windows need more KV cache per request, so fewer requests fit at once.

See Tensor parallel

Preemption

What a serving engine does when the KV cache runs out mid-answer: it pauses a request, frees its memory and recomputes it later. vLLM picks the most recently admitted request.

On the bus: A rider bumped back to the stop.

See 2 · One GPU, The bus loop

Prefix caching

Reusing the KV cache of a prompt beginning that was already processed, such as a shared system prompt, instead of computing it again. On by default in vLLM.

See 4 · Beyond parallelism

Serving and scheduling

Prefill

The first phase of a request: processing the prompt's tokens together (a long prompt in a few large chunks) to fill its KV cache. It is compute-bound and decides the time to first token.

On the bus: Loading the rider's luggage at the stop.

See 1 · The problem, 2 · One GPU

Decode

The second phase: producing the answer one token per step. Each step reads all the weights to do very little maths, so decode is memory-bound.

On the bus: Driving laps.

See 1 · The problem

Decode step (iteration)

One pass through the whole model that gives every running request one more token. Everyone in the batch shares the step, so its cost is split among them.

On the bus: One lap.

See 1 · The problem, The bus loop

Batching (batch size)

Processing many requests in the same step so they share one read of the weights. The batch size is how many are in the step. It is the main lever on GPU utilisation.

On the bus: Filling the bus.

See 1 · The problem, The bus loop

Continuous batching (iteration-level scheduling)

Scheduling where finished requests leave and waiting ones join at every step, so the batch stays full.

On the bus: Riders get on and off between laps.

See 2 · One GPU, The bus loop

Chunked prefill

Splitting a long prompt's prefill into pieces spread over several steps, so one big prompt never stalls everyone else's next token. On by default.

On the bus: Loading a long prompt's bags 16 per stop over several laps, so the bus keeps moving.

See 2 · One GPU, The bus loop

Scheduler

The part of a serving engine that decides, every step, which requests run and how many tokens each one processes.

See 2 · One GPU

Micro-batch

A slice of the batch. Pipeline parallelism keeps several micro-batches in flight so every stage has work while the others are busy.

On the bus: One of several busloads on the relay at once.

See Pipeline parallel

Concurrency (in flight)

How many requests are being served at the same moment. The ceiling is set by KV cache space and by a configured cap on concurrent requests.

On the bus: Seats taken.

See 2 · One GPU, The bus loop

Queueing

Requests that have arrived but cannot start yet because the batch or the KV cache is full. Time spent here counts toward time to first token, and a queue that keeps growing means the server is over capacity.

On the bus: Riders waiting at the stop.

See 2 · One GPU, The bus loop

Load balancer

A router that sends each incoming request to one of several replicas. vLLM's data-parallel balancer picks the least busy one.

See Data parallel

Speculative decoding

A small, fast drafter guesses several tokens and the full model checks them all in one step, keeping the ones it agrees with. It spends spare compute to get more than one token per step.

See 4 · Beyond parallelism

Async scheduling

The CPU plans the next step while the GPU runs the current one, closing the idle gaps between steps.

See 4 · Beyond parallelism

CUDA graphs

A recorded sequence of GPU kernels that can be replayed with one launch, removing the overhead of starting dozens of small kernels every step.

See 4 · Beyond parallelism

Prefill/decode disaggregation

Running prefill and decode on separate pools of GPUs, each with its own layout, so long prompts never interrupt token generation. It makes latency more predictable rather than raising throughput.

See 4 · Beyond parallelism

Parallelism

Tensor parallelism (TP)

Splitting every layer's weight matrices across GPUs. All of them work on every token together and combine results twice per layer. It gives the lowest latency per token but needs a very fast link.

See Tensor parallel, 3 · Split visualizer

Pipeline parallelism (PP)

Giving each GPU a consecutive block of layers and passing activations from one to the next. It works over slow links but does not speed up a single request.

On the bus: A relay of drivers, each covering one stretch of the loop.

See Pipeline parallel, 3 · Split visualizer

Pipeline stage

One GPU, or group of GPUs, in a pipeline, responsible for one block of layers.

On the bus: One driver's stretch.

See Pipeline parallel

Pipeline bubble

Time a pipeline stage sits idle waiting for work from the stage before it. It shrinks when more micro-batches are in flight.

On the bus: A driver waiting for the next handoff.

See Pipeline parallel

Data parallelism (DP)

Running several complete copies of the model, each serving its own requests. Throughput grows almost linearly and nothing is shared, but every copy needs room for all the weights.

On the bus: More buses on the same loop.

See Data parallel, The bus loop

Replica

One complete, independent copy of the model and its serving engine.

On the bus: One bus.

See Data parallel

Expert parallelism (EP)

Spreading a mixture-of-experts model's experts across GPUs and sending each token to the GPUs that hold its chosen experts. “Wide EP” spreads them over many GPUs or servers.

See Expert parallel, 3 · Split visualizer

Context parallelism

Splitting one very long sequence across GPUs, so prompts or KV caches too big for one GPU can still be served.

See 4 · Beyond parallelism

Rank

The numbered ID of one process, usually one GPU, within a parallel group. A TP=4 group has ranks 0 to 3.

See Expert parallel

Collective

A communication pattern in which a whole group of GPUs exchanges data at once, such as all-reduce or all-to-all. Every member must take part, so the slowest one sets the pace.

See 3 · Split visualizer

All-reduce

A collective that adds up a tensor from every GPU and gives each GPU the total. Tensor parallelism needs two per layer.

See Tensor parallel, 3 · Split visualizer

All-to-all

A collective in which every GPU sends a different piece of data to every other GPU. Expert parallelism uses it to send tokens to their experts and bring the results back.

See Expert parallel, 3 · Split visualizer

Lockstep

Moving together, step for step: no GPU can start the next step until the others have finished this one. Tensor-parallel GPUs run in lockstep, and so do the data-parallel ranks of a MoE model.

See Tensor parallel, Expert parallel

Expert load balancing (EPLB)

Moving or copying popular experts so no GPU becomes a hotspot while others sit idle.

See Expert parallel

Hardware and networking

Node (server)

One machine, usually holding 4 or 8 GPUs. GPUs inside a node talk over fast links. Between nodes they use the network.

See Which split to use

Interconnect

The links that carry data between GPUs: NVLink inside a node, PCIe on cheaper cards, and InfiniBand or Ethernet between nodes. Its speed decides which split is practical.

See Tensor parallel, Pipeline parallel

NVLink

NVIDIA's direct GPU-to-GPU link, carrying from several hundred gigabytes to terabytes per second per GPU. Rack-scale systems join dozens of GPUs into one NVLink domain.

See Tensor parallel

PCIe

The general-purpose expansion bus in every computer. Gen5 x16 carries about 128 GB/s in total, several times slower than NVLink. Consumer and many workstation cards rely on it alone.

See Tensor parallel, Pipeline parallel

InfiniBand and RoCE

High-speed networks between servers. InfiniBand is a dedicated fabric. RoCE runs the same RDMA protocol over Ethernet.

See Expert parallel

RDMA (GPUDirect RDMA)

Remote direct memory access: the network card copies data straight between GPU memories in different servers without going through the CPU. Fast cross-node tensor or expert parallelism needs it.

See Expert parallel

Kernel

A single program launched on the GPU, such as one matrix multiply. A decode step launches dozens of them.

See 4 · Beyond parallelism

Speed limits

Memory bandwidth

How fast data moves between GPU memory and the compute cores, in bytes per second. During decode this, not maths speed, usually sets the pace.

On the bus: How fast the bus can drive the route.

See 1 · The problem

Memory-bound

Limited by how fast data can be read rather than how fast it can be computed. Decode with a small batch is memory-bound.

On the bus: The lap costs the same however many ride.

See 1 · The problem

Compute-bound

Limited by maths speed. Prefill is compute-bound. Very large decode batches make the weight maths compute-bound, though reading each request's KV cache stays memory-bound.

See 1 · The problem

Measuring it

Throughput

Work finished per second, usually tokens per second across the whole deployment. It decides the cost per token.

On the bus: Words per second across all riders.

See 1 · The problem, Data parallel

Latency

How long someone waits. For LLMs it is split into time to first token and the time between later tokens.

See Tensor parallel, Pipeline parallel

Inter-token latency (ITL, TPOT)

The time between successive tokens of one answer once it is streaming. TPOT, time per output token, is the same idea averaged over the answer. It sets how fast text appears to scroll.

On the bus: Lap time.

See Tensor parallel, 4 · Beyond parallelism

Time to first token (TTFT)

How long a user waits between sending a request and seeing the first token. It includes queueing and prefill.

On the bus: Waiting at the stop, loading luggage and riding the first lap.

See 1 · The problem

Percentiles: p50, p95, p99

p95 latency means 95% of requests were faster than this. p50 is the median. The high percentiles, called the tail, capture the slow experiences users complain about.

See 4 · Beyond parallelism

GPU utilisation

The share of time, or of peak capability, a GPU spends doing useful work. Idle waiting and communication count against it.

On the bus: How full the bus is, lap after lap.

See 1 · The problem, The bus loop

QPS

Queries per second: the number of incoming requests per second.

See Expert parallel
